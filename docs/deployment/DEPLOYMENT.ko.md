# 배포

특정 플랫폼을 전제하지 않습니다. 이 서버에 필요한 것은 SIGTERM을 보낼 수 있는
프로세스 관리자, 접근 가능한 PostgreSQL, 그리고 아래의 환경 변수뿐입니다.

> 영문판은 [DEPLOYMENT.md](DEPLOYMENT.md)입니다. 두 문서는 같은 내용을 담습니다.

---

## 환경 변수

`DATABASE_URL`과 `JWT_SECRET`에는 기본값이 없고, 없으면 프로세스가 시작을 거부합니다.
나머지는 `.env.example`을 참고하세요.

프로덕션에서 반드시 설정해야 하며 시작 시점에 강제되는 변수가 둘 있습니다.

| 변수 | 요구사항 |
| --- | --- |
| `COOKIE_SECURE` | `true`여야 합니다 — 아니면 리프레시 쿠키가 평문으로 오갑니다 |
| `SEED_ADMIN_PASSWORD` | **설정하지 않아야** 합니다 — 로컬 데모 계정 생성용 변수입니다 |

로드 밸런서 뒤에서는 `TRUST_PROXY=true`가 필요합니다. 이게 없으면 모든 요청 로그와
모든 세션이 클라이언트가 아니라 밸런서의 주소를 기록합니다.

시크릿은 이미지에 굽지 않습니다. 실행 시점에 환경 변수로 전달되며, Dockerfile이
`.env`를 복사하지 않는 이유도 그것입니다.

---

## 마이그레이션은 시작 시점이 아니라 배포 단계에서 실행합니다

```bash
npx prisma migrate deploy
```

애플리케이션 엔트리포인트에서 실행하면 **안 됩니다**. 롤링 배포는 여러 컨테이너를
동시에 띄우고, 부팅 시 마이그레이션은 같은 데이터베이스에서 여러 마이그레이션이
경쟁한다는 뜻입니다. Prisma가 어드바이저리 락을 잡기 때문에 보통은 손상이 아니라
컨테이너들이 서로를 기다리는 결과가 나오는데, 하필 그 시점이 용량이 가장 필요한
구간입니다.

새 버전이 시작되기 전에, 잡이나 릴리스 단계에서 한 번만 실행하세요.

### 확장 → 이행 → 축소 (expand, migrate, contract)

모든 마이그레이션은 *이전* 버전이 아직 돌고 있는 상태에서 적용돼야 합니다. 롤링
배포 중에는 두 버전이 동시에 살아 있기 때문입니다.

1. **확장** — 새 컬럼을 nullable로, 또는 기본값과 함께 추가합니다. 두 버전 모두 동작합니다.
2. **이행** — 그 컬럼에 쓰는 코드를 배포하고, 백필합니다.
3. **축소** — 옛 형태를 읽는 버전이 하나도 남지 않았을 때에만 제거합니다.

따라서 컬럼 이름 변경은 배포 한 번이 아니라 세 번입니다. 한 단계로 처리하면 경쟁에서
진 쪽 버전이 깨집니다.

## 종료

SIGTERM은 다음 순서로 드레인을 시작합니다.

1. **레디니스가 즉시 실패하기 시작합니다.** 라이브니스는 계속 통과합니다 — 프로세스가
   병든 게 아니라 떠나는 중입니다. 여기서 라이브니스가 실패하면 컨테이너는 드레인되는
   대신 죽임을 당합니다.
2. **짧은 대기**(2초). 로드 밸런서가 자기 폴링 주기로 레디니스 변화를 알아챈 뒤에
   연결 수락이 멈추도록 하기 위함입니다.
3. **`app.close()`** — 수락을 중단하고, `onModuleDestroy`(Prisma 연결 해제)를 실행하며,
   처리 중인 작업을 끝냅니다.
4. **정상 종료(exit 0).**

전체에 10초 하드 타임아웃이 걸려 있습니다. 끝나지 않을 요청이 프로세스를 붙잡고
있어서는 안 됩니다. 오케스트레이터가 결국 SIGKILL을 보낼 텐데, 그건 통제된 종료보다
나쁜 결말이기 때문입니다.

플랫폼의 종료 유예 시간(termination grace period)을 **10초보다 크게** 잡으세요.
그러지 않으면 하드 타임아웃이 실행될 기회조차 없습니다.

## 헬스 계약

| 경로 | 의미 | 용도 |
| --- | --- | --- |
| `/api/health/live` | 프로세스가 서빙 가능함. 그 외에는 아무것도 확인하지 않음. | 라이브니스 프로브, 컨테이너 헬스체크 |
| `/api/health/ready` | 트래픽을 보내도 됨. DB를 확인하고, 드레인 중에는 실패함. | 레디니스 프로브 |
| `/api/health` | 사람이 보는 요약. 항상 200이며 `degraded`를 보고함. | 대시보드 |

라이브니스 프로브를 절대 `/ready`에 걸지 마세요. 데이터베이스 장애가 함대의 모든
컨테이너를 죽이게 되는데, 그건 아무것도 고치지 못하면서 복구에 필요한 용량만
없앱니다.

## 브라우저는 하나의 오리진만 봐야 합니다

이건 취향이 아니라 제약입니다.

리프레시 토큰은 `sameSite: 'lax'`, `path: '/api/auth'`인 HttpOnly 쿠키입니다.
프론트엔드가 이 API와 다른 오리진에서 서빙되면 브라우저는 그 쿠키를 보내지 않습니다.
로그인은 되는 것처럼 보이다가, 액세스 토큰이 만료되는 순간 아무 설명 없이 세션이
끝납니다. 두 개의 WebSocket 게이트웨이(`/api/topology`, `/api/live/chat`)도 같은
방식으로 실패합니다.

세 개의 프론트엔드(React, Vue, Next.js)가 이 백엔드를 공유하므로, 어느 하나에
묶어 넣을 수 없습니다. **대신 각 프론트엔드가 `/api`를 이 서버로 프록시합니다.**
개발 환경에서는 Vite 프록시 또는 Next rewrite이고, 프로덕션에서는 정적 빌드를
서빙하는 호스트의 rewrite 규칙입니다. 어느 쪽이든 브라우저는 하나의 오리진을 보고,
이 이미지는 프레임워크에 중립인 채로 남습니다.

CORS와 함께 `sameSite: 'none'`을 쓰는 것이 대안이고 그러면 프록시가 필요 없습니다.
대신 `lax`가 공짜로 주는 CSRF 방어를 잃고, 그걸 토큰으로 대체해야 합니다. 그래서
여기서는 기본값이 아닙니다.

`CLIENT_DIR`는 여전히 존재하며 이 프로세스에서 빌드된 프론트엔드를 서빙합니다.
더 이상 배포 방식은 아니지만, 프록시 없이 단일 오리진 구성을 로컬에서 재현하는
가장 짧은 방법입니다.

## 이미지

API만 담습니다. 세 프론트엔드가 `/api`를 이쪽으로 프록시하게 되면서 클라이언트
스테이지는 빠졌습니다.

```bash
docker build -t boilplate-server .
docker run --rm -p 3001:3001 \
  -e DATABASE_URL=... -e JWT_SECRET=... -e COOKIE_SECURE=true -e NODE_ENV=production \
  boilplate-server
```

멀티 스테이지입니다. TypeScript 툴체인과 테스트 러너는 빌드 스테이지에 남습니다.
Prisma CLI는 남지 않습니다 — `prisma migrate deploy`는 이 이미지 안에서 실행되는
배포 단계이고, 그것 없이 배포하면 위의 절차를 수행할 수 없게 됩니다. CI는 빌드된
이미지 안에서 이 명령이 실제로 해석되는지 검증합니다. 그렇다고 적어둔 주석은 검사가
아니기 때문입니다.

이미지의 non-root `node` 사용자로 실행됩니다. 헬스체크는 라이브니스만 호출하므로,
떠 있지만 데이터베이스를 기다리는 컨테이너는 "살아 있지만 준비되지 않음"으로
보고됩니다 — 롤링 배포가 봐야 하는 상태가 바로 그것입니다.

`NODE_ENV=production`은 `COOKIE_SECURE`가 false면 시작을 거부합니다. 평문 HTTP
배포가 리프레시 쿠키를 그대로 흘려보내는 대신 부팅 시점에 실패하도록 만듭니다.

## 배포 절차

서비스는 넷입니다. 이 서버 하나, 그리고 프론트엔드마다 하나씩. 각 저장소의
`render.yaml`이 자기 서비스를 기술하므로, 블루프린트는 대시보드에 타이핑되는 대신
코드와 함께 리뷰됩니다. 대시보드에서 바꾼 설정은 흔적을 남기지 않습니다.

**순서가 중요합니다.** 프론트엔드는 이 서비스의 URL이 필요하고, 이 서비스는
프론트엔드의 URL이 필요합니다.

1. **이 서비스를 먼저.** `render.yaml`로 생성합니다. `DATABASE_URL`, `JWT_SECRET`,
   `CORS_ORIGINS`를 물어봅니다. `CORS_ORIGINS`는 일단 임시값으로 두세요 — 4단계에서
   채웁니다. `JWT_SECRET`은 새로 생성하세요. 개발용 값은 개발자 머신과 셸 히스토리에
   남아 있었습니다.
2. **마이그레이션 적용.** 무료 인스턴스 타입에는 pre-deploy 명령이 없으므로, 같은
   `DATABASE_URL`을 가진 아무 곳에서나 `npx prisma migrate deploy`를 실행하세요.
   그 다음 `npx prisma migrate status`가 대기 중인 마이그레이션이 없다고 보고해야
   합니다. 엔트리포인트에서 실행하지 마세요 — 이유는 위에 있습니다.
3. **프론트엔드들.** 각 블루프린트가 백엔드 주소를 물어봅니다. React와 Vue는
   `BACKEND_ORIGIN`, Next는 `BACKEND_URL`입니다. 1단계에서 이 서비스가 받은 URL을
   넣으세요.
4. **다시 `CORS_ORIGINS`로.** 세 프론트엔드의 오리진을 쉼표로 구분해 설정하고 이
   서비스를 재배포하세요. 이건 CORS만의 문제가 아닙니다. **WebSocket 핸드셰이크는
   애초에 CORS의 적용을 받지 않으므로**, 이 목록이야말로 외부 사이트가 브라우저의
   쿠키로 인증된 소켓을 여는 것을 막는 장치입니다. 이걸 틀리면 모든 소켓이 4401로
   닫히는데 — 인증 버그처럼 보이지만 인증 버그가 아닙니다.

### 무료 인스턴스에서 달라지는 것

무료 서비스는 트래픽이 15분간 없으면 내려가고, 다시 올라오는 데 1분쯤 걸립니다.
따라서 조용했던 뒤의 첫 요청은 타임아웃되거나 멈춘 것처럼 보이고, 그 사이에 열려
있던 WebSocket은 닫힙니다. 재연결과 리싱크 경로가 이 상황을 정상적으로 처리합니다 —
연결이 끊긴 것과 같은 경우이기 때문입니다. 다만 방문자의 첫 클릭은 느릴 것이고,
그건 애플리케이션이 아니라 요금제의 성질입니다.

## 확장 한계, 있는 그대로

오늘 기준 프로세스 단위인 것이 셋 있고, 인스턴스가 둘 이상이면 잘못 동작합니다.
각각에는 이름 붙은 이음매가 있습니다.

| 항목 | N개 인스턴스에서의 동작 | 이음매 |
| --- | --- | --- |
| 로그인 스로틀링 | 시도 허용량이 N배가 됨 | `LOGIN_ATTEMPTS` |
| 채팅 전송 스로틀링 | 메시지 허용량이 N배가 됨 | `ChatRateLimiter` |
| 실시간 팬아웃 | A에서 발행된 이벤트가 B의 클라이언트에 도달하지 않음 | `TopologyBroadcaster`, `ChatBroadcaster` |

팬아웃은 단순히 약해지는 게 아니라 눈에 보이게 틀리는 항목입니다. 시청자 절반이
업데이트를 못 받습니다. 공유 어댑터가 생기기 전까지는 인스턴스를 하나만 돌리거나,
같은 그래프·방송에 대한 모든 WebSocket을 같은 인스턴스로 라우팅하세요.

## 아직 검증되지 않은 것

- **Docker 이미지를 로컬에서 빌드해본 적이 없습니다.** 이 머신에 Docker 데몬이
  없습니다. CI의 `docker` 잡이 이미지를 빌드하고 컨테이너를 스모크 테스트합니다 —
  데이터베이스 없이 라이브니스는 응답하고 레디니스는 응답하지 않으며, 마이그레이션
  단계가 필요로 하는 Prisma CLI가 이미지 안에서 해석됩니다.
- **부하 테스트를 하지 않았습니다.** 기준 수치를 주장하지 않습니다. 유계 큐, 병합,
  느린 소비자 연결 해제는 코드로 논증되고 단위 테스트로 덮여 있지만, 그중 어느 것도
  측정값은 아닙니다.
- **배포된 서비스는 데모 사이에 서스펜드해 둡니다.** Render 무료 티어에서 돌기
  때문입니다. 인스턴스를 계속 띄워두면 월 750시간을 8일 만에 다 씁니다. 콜드
  스타트는 약 20초가 걸리고, 잠든 인스턴스에 병렬 요청을 몰면 깨우는 대신
  `x-render-routing: hibernate-rate-limited`와 함께 `429`로 답합니다 — 그래서 각
  프론트엔드는 조급한 여러 번이 아니라 참을성 있는 한 번으로 깨웁니다.

이 목록에 있었으나 이제 닫힌 항목이 넷 있습니다.

- **배포됐습니다.** `render.yaml`이 네 서비스를 기술하고, 넷 다 그것으로부터
  실행됐습니다. 특히 닫힌 것은 플랫폼 프록시 뒤에서만 보이는 것들입니다 —
  `TRUST_PROXY`, TLS 종료, 그리고 WebSocket의 유휴 타임아웃.

- 세 프론트엔드 모두 실제 소켓으로 이 서버와 통신했고, 이 서버를 상대로 로그인했으며,
  동일한 채팅·토폴로지 기능을 이 서버로부터 구동했습니다. 각각이 `/api`를 프록시하므로
  브라우저는 단일 오리진을 봅니다.
- 마이그레이션은 오프라인에서 작성됐고, 이후 이 머신에서 호스팅형 PostgreSQL을 상대로
  `migrate deploy`로 적용됐습니다. `migrate status`는 대기 중인 것이 없다고 보고하며,
  CI의 `integration` 잡이 마이그레이션을 재생하면 `schema.prisma`가 정확히 재현됨을
  증명합니다.
- 두 WebSocket 게이트웨이 모두 실제 소켓으로 검증됐습니다. 핸드셰이크 인증이 유효한
  토큰을 받아들이고 누락되거나 위조된 토큰에 4401로 닫았으며, HTTP로 전송한 채팅
  메시지가 참여 중인 구독자에게 도착했고, 발행된 토폴로지 이벤트가 실제 브라우저의
  카운터를 바꿨습니다.
